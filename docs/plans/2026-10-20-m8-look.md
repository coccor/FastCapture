# M8: The Look Implementation Plan

> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax for tracking. Each part ends with `cargo test`, `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` passing, screenshots of what changed in light and dark, and one commit. Code comments never cite the spec. FastPad (`C:\Projects\Fastpad`) is read for reference and never edited.

**Goal:** FastCapture looks like FastPad's sibling. Every window, menu and confirmation uses FastPad's palettes, type and shapes, in a light or dark theme, or **System**, which follows Windows and changes as Windows does. No new crates.

**Spec:** `docs/specs/2026-10-18-fastcapture-design.md` §11 (Look), §16.

**Found before planning (2026-10-20):**

- **FastPad's direction** (its design-token specs and `src/window/palette.rs`, `design/`): semantic color roles with one owner each, a 4 px grid, two radii (4 px for fields, rows and buttons; 8 px for tabs), one focus ring (2 px accent with a 1 px gap), a type ramp (Body 13 px, Heading 14 px semibold, Title 18 px semibold in pixels at 96 DPI), Segoe UI Variable Text and Display with Segoe Fluent Icons on Windows 11, and Segoe UI with Segoe MDL2 Assets elsewhere. Text follows Windows' text-size setting. It has no Mica and no motion. Its spec says: "No Mica, no motion, no themed confirmation dialog." A contrast test guards every theme: 4.5:1 for text and 3:1 for the accent. High contrast uses `GetSysColor` pairs with square corners.
- **FastPad's Light and Dark palettes**:

  | content | 255,255,255 | 30,30,30 |

  The close button turns red (196,43,28) on hover.
- **How FastPad themes:**
  - **System:** it reads `AppsUseLightTheme`, and on `WM_SETTINGCHANGE`, `WM_THEMECHANGED` or `WM_DWMCOLORIZATIONCOLORCHANGED` it reads again, re-theming only on a real change.
  - **Windows:** its own windows are borderless with a painted title strip and 46 px caption buttons. Dialogs get rounded DWM corners and a 1 px frame extension for the shadow, and the frame gets `DWMWA_USE_IMMERSIVE_DARK_MODE`.
  - **Controls:** surfaces are painted with GDI, with analytic coverage on rounded corners. Native edits are colored through `WM_CTLCOLOR*`, and scroll bars get `SetWindowTheme("DarkMode_Explorer")`. Its context menus are native and stay light, since it avoids uxtheme's undocumented exports.
- **FastCapture today:**
  - `ui/theme.rs` has a small palette of its own: other values than FastPad's, read once when a window opens and never again, and no setting.
  - The capture box follows Windows light or dark.
  - The review window darkens its frame, list and preview, but its list header stays light. A screenshot of the review example with Windows in dark mode showed it light, so even that needs checking.
  - Settings and the home picker are standard dialog-grey controls in both themes.
  - The tray menu, the capture box's attachment menu and three confirmations (the 20 MB file question, discarding a note, the Cloud first-use screen) are native menus and message boxes, always light.

**Decided for M8:**

- **The palettes are FastPad's Light and Dark, value for value**, in one `Palette` with FastPad's role names. Windows set in FastPad's units (pixels at 96 DPI, scaled by DPI and text size) keep the same proportions. FastPad's Catppuccin and Paper/Lamp themes aren't in M8.
- **`theme=system|light|dark`**, `system` by default. Settings shows it as a three-way choice at the top. A change from Settings or from Windows reaches every open window at once. The tray app forwards Windows' change messages to its windows, so a window that is open but hidden still catches up.
- **Standard controls stay standard, painted by FastCapture.** Unlike FastPad's Settings, which is painted from scratch, FastCapture subclasses its buttons, check boxes, radio buttons, combo boxes and list view, and paints them from the palette. They keep their keyboard handling, focus and what screen readers announce, which the Settings window promised in M2. Check boxes are drawn as FastPad's toggle switches, radio pairs as a segmented choice, and push buttons with 4 px corners (the primary one in the accent). Edits are colored through `WM_CTLCOLOREDIT`; combo lists through `WM_CTLCOLORLISTBOX`; and scroll bars get `DarkMode_Explorer`.
- **FastCapture's windows get FastPad's dialog frame**: borderless, with a painted title strip (title, then minimise, maximise where it makes sense, and close, using Fluent glyphs), rounded DWM corners, the 1 px frame extension for the shadow, and the dark frame attribute. Snap, the system menu (Alt+Space) and dragging the strip all still work, with the native caption reclaimed in `WM_NCCALCSIZE` as FastPad does.
- **Menus and confirmations are painted too, going one step past FastPad.** The tray menu, the attachment menu and the three confirmations become a small painted popup and a painted message window, keyboard-first (arrows, Enter, Esc, access keys) and with accessible names. This needs none of uxtheme's undocumented exports. Notifications stay Windows' own.
- **High contrast** uses Windows' colors and square corners, as in FastPad. It is re-checked on the same change messages.

## What M8 does not do

- FastPad's Catppuccin and Paper/Lamp themes, and following the Windows accent color (still open in FastPad too).
- Mica or any other backdrop, and animation.
- Restyling notes or the Markdown FastCapture writes. M8 is FastCapture's own windows only.
- A second tray icon for light taskbars: the drawn icon already reads on both (M1).

## Architecture

```
src/
  ui/
    theme.rs          (changed) FastPad's roles and values, the resolver (setting + Windows + high contrast),
                      the type ramp, metrics, contrast checks; change notification to open windows
    paint.rs          rounded fills and rings with analytic corners, glyphs, text in the ramp
    frame.rs          the borderless dialog frame: title strip, caption buttons, hit-testing, DWM attributes
    controls.rs       painted buttons, toggles, segmented choice, combo faces, list view rows and header
    popup.rs          the painted menu and message window
    capture_box.rs    (changed) FastPad's palette and live re-theme
    settings.rs       (changed) the frame, painted controls, the Theme choice
    review.rs, review_list.rs, home_picker.rs  (changed) the frame, painted list, live re-theme
    app.rs            (changed) Windows' change messages forwarded; the tray menu as a popup
  config/
    settings.rs       (changed) `theme`
```

## Parts

### Part 1: Tokens and the theme setting

- [x] `ui/theme.rs`: FastPad's roles with its Light and Dark values; the high-contrast palette from `GetSysColor`; `Theme { System, Light, Dark }` resolved against `AppsUseLightTheme` and `SPI_GETHIGHCONTRAST`.

  As built:
  - **Layout:** `ui/theme/` holds `mod.rs` (the palette and resolver), `faces.rs`, `ramp.rs`, `metrics.rs` and `contrast.rs`.
  - **Role names:** FastPad's `editor_*` roles are `content_*` here, and FastPad's editor-only roles (caret line, line numbers) are left out.
  - **Selected rows:** they use `hover_foreground`, because FastPad's dark text (212) on its selection blue is only 4.10:1, while its hover text (240) is 5.3:1. The values themselves stay FastPad's.
  - **Tests:** like FastPad's, they never read the machine's theme or text size.
  - **High contrast:** it needs `windows-sys`'s `Win32_UI_Accessibility` feature.
  - **Existing windows:** the capture box and the review window now draw with the new values under the old roles' names. Part 5 lays them out properly.
- [x] The type ramp:
  - Segoe UI Variable Text and Display, chosen when Windows is build 22000 or later and the face exists;
  - Segoe Fluent Icons or Segoe MDL2 Assets for glyphs;
  - sizes in pixels, following `TextScaleFactor`.
- [x] Metrics: the 4 px grid, the radii, the focus ring, the strip and button sizes.
- [x] `config/settings.rs`: `theme=system|light|dark`, warning on anything else.
- [x] `ui/app.rs`: `WM_SETTINGCHANGE`, `WM_THEMECHANGED` and `WM_DWMCOLORIZATIONCOLORCHANGED` re-resolve the theme, and so does saving Settings; on a real change every open window gets `WM_FASTCAPTURE_THEME`. The message is registered (`FastCapture.ThemeChanged`), so it can't collide with a window's own `WM_APP` messages, and it is posted to every top-level window of the UI thread, hidden ones too. No window handles it yet: Parts 4 and 5 do. No screenshots this part: nothing is laid out differently, and the capture box's new colors are checked in Part 5.
- **Tests:**
  - the values equal FastPad's;
  - contrast is 4.5:1 for text and 3:1 for the accent in every palette;
  - the resolver for each setting, light or dark, and high contrast;
  - settings round trip.

### Part 2: The painting kit and the frame

- [x] `ui/paint.rs`: filled and bordered rounded rectangles and rings with analytic corner coverage (FastPad's approach, in GDI); text in the ramp; Fluent glyphs; a double-buffered paint helper so nothing flickers.
- [x] `ui/frame.rs`: the borderless frame.

  As built:
  - **Client area:** the whole window. A maximized window's is the monitor's work area. The resizing edges are hit-tested inside the window, not outside it as Windows' own frame does.
  - **Window style:** windows keep a captioned style, so DWM still draws the rounded corners and the shadow, and the frame doesn't extend into the client area.
  - **Caption buttons:** their click is posted as a `WM_SYSCOMMAND`, so it is safe while the window is busy. Clicking Close goes through the system's Close, and `WM_CLOSE` handlers still run. The buttons keep their targets right up to the window's edge, so the close button can be hit in the corner.
  - **Title:** it turns muted when the window is inactive.
  - **`examples/look.rs`** shows the frame and the kit in any theme, for checking by eye. Screenshots in light and dark: the strip, the accent button, bordered buttons with the focus ring, rows with the selection bar, and muted and error text.
  - The painted title strip and caption buttons, with hover, pressed and the red close.
  - Hit-testing for dragging, Snap layouts on maximise (`HTMAXBUTTON`), and resizing edges.
  - `WM_NCCALCSIZE`.
  - Rounded corners, the shadow extension, and the dark frame attribute, reapplied on a theme change.
- **Tests:** coverage values at corners; hit-testing at each part of a frame at 100, 150 and 200 % DPI; a frame window created, re-themed and destroyed. Also: pixels sampled from rounded fills, bordered boxes, the focus ring and text drawn into a bitmap; the strip's title and red close; a real framed window whose client is the whole window, whose strip, close button and edges hit-test right, and that closes from its button. The layout is checked at 100, 150 and 200 %, and hit-testing at 100 %.

### Part 3: Painted standard controls

- [x] `ui/controls.rs`:
  - push buttons, plain or primary;
  - check boxes drawn as toggle switches;
  - radio groups drawn as a segmented choice;
  - combo box faces, with their lists colored;
  - edits colored, with the focus ring drawn around the focused field;
  - list view rows (hover, selection, inactive selection) and its header painted;
  - scroll bars themed.

  Each control is subclassed: it keeps its own messages and state, and FastCapture only paints it.

  As built:
  - **One subclass, `paint_as(control, Look, Surface)`.** It paints from `theme::current()` every time, so a theme change is only a repaint, which `controls::retheme(window)` does for every child along with the scroll bars and list colors.
  - **Push buttons, toggles, segments and combo faces** are painted in `WM_PAINT` and `WM_PRINTCLIENT`. A button draws itself at once on a click, a key or a state change, so it is invalidated after each and painted again.
  - **The default button** (`BS_DEFPUSHBUTTON`) is the accent. Faces are a little darker or lighter under the pointer and when pressed.
  - **The focus ring** shows only once the keyboard is used (`UISF_HIDEFOCUS`), as Windows' own.
  - **Fields** (edits and list boxes) keep Windows' painting and get their border painted over it in `WM_NCPAINT`: 2 px with `WS_EX_CLIENTEDGE`, 1 px with `WS_BORDER`, rounded, the accent while focused. Edits get 6 px margins.
  - **Combo boxes:**
    - an editable one keeps its own edit, colored through the combo;
    - its list gets the theme's colors and scroll bars;
    - its face gets `WS_CLIPCHILDREN` so it never paints over the edit.
  - **Colors for fields and labels:** `colors()` answers a window's `WM_CTLCOLOR*`. Read-only and disabled edits, which ask as statics do, get the field colors.
  - **List views:** `paint_list` sets a list view's colors and paints its header, and the parent's `NM_CUSTOMDRAW` goes to `list_rows`, which paints FastPad's rows. A `tint` callback lets a window color one cell's text.
  - **List boxes:** owner-drawn ones use `draw_list_item`.
  - **The `look` example** now has real controls next to the drawn ones. Screenshots in light and dark: the segmented Local/Cloud choice, both kinds of combo box, a field, toggles on and off, and buttons. The first screenshot found Windows' own border showing through the field's rounded corners, which is fixed.
- **Tests:** each control painted into a bitmap in light, dark and high contrast, its colors sampled; keyboard state (focus, checked, disabled) shown; what MSAA reports for a toggle is still a checked check box. As built, through `WM_PRINTCLIENT`: buttons plain and default in both themes; a toggle off, then clicked on, still a `BS_AUTOCHECKBOX` reporting `BST_CHECKED` (what MSAA reads, so MSAA itself isn't called); segments; a combo box with its choice; field and label colors; a list view's selected row (inactive) and header; high contrast's square corners.

### Part 4: Settings and the home picker

- [x] `ui/settings.rs`:
  - the frame;
  - the form laid out in FastPad's settings rhythm: 20 px padding, section headings in the ramp, 26 px controls, and a footer with Open settings file, Save and Cancel;
  - **Theme** (System, Light, Dark) as the first row, previewed in the window as soon as it is chosen and saved with the rest;
  - every control painted;
  - the status and test lines in muted text, and problems in the error color.

  As built:
  - **Layout:** the window keeps its layout, now under the 40 px strip and a Theme row, with 26 px fields and toggles 28 px high. Local/Cloud became two equal segments.
  - **Frame:** the client area is the whole window, and `WS_CLIPCHILDREN` keeps its painting off the controls.
  - **Theme choice:** it is shown at once, through `theme::tell_windows`, so every open window previews it. Closing without saving reads the file's theme back.
  - **Dimmed labels:** a disabled label draws its own embossed grey whatever the theme, so the unused mode's labels stay enabled and are dimmed through their color. The first dark screenshot showed the emboss.
  - **Tokens line:** it now spans the window, since the larger font cut it.
  - **Not done:** `WM_DPICHANGED` still isn't handled; the window keeps the DPI it opened at, as before.
- [x] `ui/home_picker.rs`: the frame, the box and the list painted. The list is owner-drawn (`LBS_OWNERDRAWFIXED | LBS_HASSTRINGS`) with FastPad's 26 px rows, and the box is a field with the accent border while typing. It follows theme changes while open. `examples/look.rs -- dark home` opens it on its own.
- **Tests:** the window's existing tests still pass; Theme round-trips through the file; switching the choice re-themes the open window; screenshots in light, dark and high contrast. As built: the form's round trip, and a window test where Dark is shown when chosen, put back on Cancel, and kept on Save. Screenshots of Settings and the home picker in light and dark. High contrast can only be turned on in Windows' own settings, so it is checked by the controls' tests, not by screenshots; Part 7's pass covers it by hand.

### Part 5: The capture box and the review window

- [x] `ui/capture_box.rs`: FastPad's palette and ramp in place of the old one; live re-theme.

  As built:
  - **Already FastPad's design:** the box keeps it, with the same roles, square chips, and its own borderless frame.
  - **What changed:** the title is Heading and the text Body; the edit's scroll bars follow the theme in light too; the frame goes through `frame::apply_theme`, so high contrast gets square corners; painting is double-buffered.
  - **Theme changes:** the box takes the theme when it changes and again when the hotkey brings it back.
  - **Screenshots** in both themes come from `examples/look.rs -- dark capture`.
- [x] `ui/review.rs`, `ui/review_list.rs`:
  - the frame;
  - the list painted (rows, header, state chips), the preview colored, the status line in the strip color;
  - live re-theme;
  - why the example opened light under a dark Windows found and fixed.

  As built:
  - **Why it opened light:** the old palette read `AppsUseLightTheme` from a key path ending in a literal `\0` (a raw string), so it never found the setting and always fell back to light. Part 1's resolver doesn't.
  - **Frame:** the window uses it with minimize and maximize, and its count is in the strip's title.
  - **List:** `controls::paint_list` and `list_rows` draw it; a failed capture's State is in the error color.
  - **Row height:** rows are FastPad's 26 px, through an empty small image list, the list view's only way to set a row height.
  - **Panes:** both have field borders.
  - **Crash found and fixed:** the first run crashed the tests (`0xC000041D`) inside the list's custom draw. `paint::text` passed an empty string's dangling pointer to `DrawTextW`, which reads it even for a count of 0. Empty text now draws nothing, with a test.
  - **`examples/review_window.rs -- --sample <folder> dark`** fills a scratch notebook with three captures. Screenshots in both themes.
- **Tests:** existing tests; a theme change re-colors an open window; screenshots in both themes. As built: the capture box and the review window each take a new theme while open, and the review list's rows are painted (checked by pixel), and empty text is safe to draw.

## Testing approach

- **Pure:** palettes, contrast, the resolver, coverage, hit-testing.
- **Windows:** windows and controls created and driven through messages, painted into bitmaps and sampled.
- **By eye:** screenshots of each window in each theme, checked against FastPad's.

## Order and dependencies

Part 1 first, then 2 and 3, which every window needs. Parts 4, 5 and 6 can each go on their own after 3. Part 7 comes last.
